# Programme plan

- **Status:** draft
- **Tool:** `odw plan` (`src/odw/plan.py`); formats in [workspace schemas](workspace-schemas.md) (`task`, `decisions`, `plan-mirror-config`, `plan-mirror`)

A programme is a piece of maintainers' work that spans many sessions and repositories. Its state lives in files, never in a session, so any person or agent can resume it.

## Layout

| Path | Content |
|---|---|
| `tasks/<id>.toml` | One task record per file, so sessions working in parallel never edit the same file |
| `tasks/INDEX.md` | The readiness view, generated by `odapkit plan render`. A programme worked by several sessions at once keeps it out of git: it depends on every task file, so a committed index collides between sessions. A programme worked by one session may commit it and check it with `render --check` |
| `decisions.toml` | The decisions only the maintainers can take, and the technical calls taken under delegation |
| `homes.toml` (`opendap.homes/v1`) | Every rule the programme introduced, and its permanent homes: a workspace-relative `path` and a phrase it `contains`; a rule still waiting for a decision names it in `pending` |
| `mirror.toml` (`opendap.plan-mirror-config/v1`) | The public tracking mirror: the GitHub `repository` of the RFCs, the `workspace` repository, the issue `label`, the RFC each phase applies (`[phase_rfc]`), per-task RFC overrides (`[task_rfc]`) and public titles (`[public_title]`) |
| `<workspace>/.state/claims/<id>.toml` | Who works on a task now (`task`, `session`, `since`, `expires`); runtime coordination outside git |

## Rules

- A task is **ready** when its status is `todo`, every task it depends on is `done` and every decision blocking it is `decided`. `next` is the first ready task by phase, then id.
- `claim` takes a ready task (or renews your own claim): status `doing` and a claim file. A live claim of another session is refused; an expired one is free. `release` drops the claim and puts a `doing` task back to `todo`. `claim`, `release`, `done` and `render` take `--dry-run`: they validate as usual, name the files they would change and write nothing. `get ID` prints one task record (`opendap.task/v1` with `--json`); `show` is its former spelling and still works. `list --json` and `next --json` print `opendap.plan-tasks/v1` (`schemas/plan-tasks.schema.json`): the tasks in `items`.
- `done` needs at least one evidence commit (`REPO=SHA`) and the docs the task updated; it removes the claim. The task schema refuses a `done` record without them.
- `check` reports schema errors, file names that do not match their id, unknown dependencies or decisions, dependency cycles, and public tasks that carry private facts (repositories all private, or a private path in the title or notes), since public tasks are mirrored as public issues. Programmes run `check` in their repository's pre-commit.
- `homes` lists the rules found only in the programme: a rule with no home, a home that is missing, or a home that no longer states the rule (case and spacing ignored). It exits 1 while any is listed; a programme ends when it exits 0, so deleting the programme loses no rule.
- Records are written with a fixed field order so diffs stay small.
- A refused action is an error with a stable code (`task.not_found`, `task.claimed`, `task.not_ready`, `task.invalid`, `task.no_evidence`; `programme.not_found` when there is no programme), a hint and a fix (a command), exit status 1 (2 for no programme); with `--json` also an `opendap.error/v1` document on stdout.
- A programme file that is not valid TOML is such an error, never a traceback: `task.invalid` (a task file), `decisions.invalid`, `claim.invalid`, `homes.invalid`, `mirror.invalid_config` (exit 2), its message `<file>:<line>:<column>: not valid TOML: …`, with `file`, `line` and `column` in the JSON error. Every command that reads the file reports it, `check` and `render --check` included, so the pre-commit hook names the file and line.
- Sessions set `ODAP_SESSION` to name themselves in claims; otherwise the tool uses user, host and parent process.

## Public tracking mirror

`odw plan mirror [--workspace DIR] [--dry-run] [--json]` publishes the public part of a programme as GitHub issues: one tracking issue per accepted RFC, in the RFC repository named by `mirror.toml`.

- **Tasks.** Only tasks with `visibility = "public"`. A task applies the RFC named in `[task_rfc]`, else the first `RFC NNNN` in its public title, else the RFC of its phase in `[phase_rfc]`. A task whose RFC is not found or not Accepted is listed as `unmapped` and mirrored nowhere.
- **Issue.** Title `Tracking: <the RFC's title>`. The body starts with the hidden marker `<!-- odapkit plan mirror: rfc NNNN -->`, links the RFC, counts the tasks done, and lists each task as a checklist item: id, public title (its `[public_title]` entry, else its title), status, and the evidence commits of public repositories as `owner/repo@sha`. Sources, notes and evidence from private repositories are never read into it.
- **Guard.** Before anything is printed or sent, the text is checked for private facts: a `private/` path, the name or slug of a repository listed under `private/` in any `repos.tsv`, a path of the programme's own files, or one of its decision ids. Any one refuses the run (`mirror.private_fact`, exit 1); the fix is a `[public_title]` entry, a reworded title or a private task.
- **Publishing.** The real run creates the label when missing, then creates or updates each issue, matched by the marker on the first line of the body and by the issue's author being the account that runs the mirror. An issue whose text is current is left alone (`unchanged`), so the run is idempotent. It never closes, reopens, deletes or edits any other issue. `--dry-run` prints the issues and reaches nothing; GitHub is reached through `gh api`.
- **Output.** `--json` prints `opendap.plan-mirror/v1` (`schemas/plan-mirror.schema.json`): `issues` (with `action` and `url` after a real run) and `unmapped`. Errors: `mirror.no_config` and `mirror.invalid_config` (exit 2), `mirror.private_fact` and `mirror.github` (exit 1).
